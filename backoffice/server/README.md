# Supabase metadata backend

`domain.mjs` is transport-neutral and uses only HTTPS PostgREST with the authenticated user's access token and the public publishable key. It does not import Node HTTP/SQLite or a service-role key. The HTTP/auth layer maps `/admin/api/*` to logical `/api/*` and provides origin/CSRF/cookie checks; PostgreSQL independently checks the current user, confirmed email, non-anonymous/non-banned status, unexpired JWT at AAL2, extant same-user AAL2 session linked to a currently verified same-user TOTP/phone/WebAuthn factor, and exactly one active database membership on every call. No browser role, organization, JWT user_metadata, email match or first signup grants authority.

The additive migration creates only `public.dg_bo_*` tables/RPCs and `dg_bo_private` helpers. New tables have RLS and no anonymous/authenticated direct privileges or permissive policies. Private schema/helpers are inaccessible to clients; the two public SECURITY DEFINER RPCs use empty search paths and explicit immutable context. Existing project objects, including `public.rls_auto_enable()`, are untouched. Its previously observed advisory warnings require separate review.

## Stored behavior

- `GET /api/state/:key` retains the eight original non-support bucket contract. Only administrator `state.write` updates infrastructure and original 8+8 wizard metadata. Other legacy mutations return `LEGACY_MUTATION_UNAVAILABLE`; simulated payments/invitations/mail/provider actions cannot be saved through these buckets. State is scoped by workspace, user, role and immutable organization. Batch CAS is atomic. PostgreSQL independently checks copied source field schemas and cross-field guards, invalidates later attestations when identity/earlier inputs change, and prohibits example inventory registration. These are operator reports, never live deployment/hardening/monitoring proof.
- `/api/integrations` stores all 15 validated installation dossier kinds. Environment derives from the database workspace; mode is `metadata_only`. Every POST requires an Idempotency-Key. PUT uses revisions, preserves historical tests, and invalidates current evidence when substantive fields change. Test is explicitly simulated. Preview has no external changes. Activate always saves/returns blocked; pause changes metadata only. Other schema-less concepts are refused.
- `/api/support/*` stores normalized tickets, public messages, internal notes and actor-scoped drafts. Client access is restricted to its actual membership organization; staff also need action permissions. Internal notes/assignment do not change a client's DTO, revision, counts, latest message, timestamps or ordering. Cached operation fingerprints include current permissions so permission revocation cannot replay old internal payloads. Replies/status transitions, CAS, matching draft clearing, audit and idempotent receipts commit together. Public/internal channels each cap at 500 messages; lists return at most 200 with `hasMore`. Plaintext bodies max 8,000 chars, subject 160; attachments/email are unavailable.
- Customer import is bounded to one manually entered record, `sourceType=manual`, `resourceReference=unlinked`. Preview binds actor, workspace, integration revision, SHA-256 configuration/plan digest, registry revision and 15-minute expiry. Commit is atomic and deduplicates stable source/batch/line IDs. Changed source payload/name conflicts require review; email never auto-merges organizations. Organizations always have billing paused and services unlinked. No invite, bill, payment, provider or external credential operation occurs. Import receipts retain original integration revision/digest; registry computes whether they still match the current dossier. Registry lists cap at 500 and receipts at 200.
- Jobs/audit are workspace-scoped staff resources. Audit stores action/IDs/revision/digests, never ticket subjects/messages or credentials. Events/messages are append-only. Secret patterns/fields and prototype keys are rejected in SQL as well as in JavaScript. Per-workspace transaction locks serialize CAS/import/idempotency decisions. Failed commands roll back their complete subtransaction; expected blocked activation is explicitly persisted with its 409 receipt.

Membership permissions are explicit database text arrays: `state.read`, `state.write`, `integrations.{read,manage,test,preview,activate,pause}`, `support.ticket.{read,create,reply,status,manage,internal_note}`, `support.draft.{read,write}`, `customer.{read,import.preview,import.commit}`, `jobs.read`, `audit.read`. Staff-only commands additionally require database role admin/support; original infrastructure requires admin. No membership/user/customer/provider sample is seeded.

## Verification and release gate

Run `node --test tests/backoffice-domain.test.mjs` for pure transport/schema tests. For actual SQL contracts set `DG_BO_TEST_DATABASE_URL` to an explicitly local disposable PostgreSQL16+ connection and run `node --test tests/backoffice-domain-sql.test.mjs`. The connection user needs CREATEDB and fixture role-creation rights. The runner creates a random temporary database, stubs only relevant Supabase Auth schema/helpers, applies the actual migration, tests ACL/MFA/revocation/IDOR/privacy/CAS/idempotency/rollback/import/bootstrap behavior, and drops that database. It never connects to the real project; absent the environment variable this SQL suite is explicitly skipped. Official PostgreSQL16.15 was used locally; the observed target project is PostgreSQL17.11. Real Supabase/PostgREST deployment remains a separate qualified acceptance step.

`supabase/bootstrap-owner.sql` is a separate trusted manual step for the user-confirmed initial email `info@dgwebservices.nl`. It requires the independently verified exact Auth UUID supplied in the same SQL session via `dg_bo.bootstrap_user_id`, a unique confirmed eligible matching Auth user, and refuses conflicting existing memberships/configuration. It sends no mail and does not create an Auth user. Repeating the exact bootstrap is idempotent; changed/disabled rights are never overwritten. Neither migration nor bootstrap has been applied to the real project during this implementation.

Deployment readiness: the verified VPS service launches native `next start` bound to loopback. Keep browser HTTPS Origin → trusted request URL handling in the acceptance checks. The alternate Vinext Node `start:worker` adapter ignores forwarded HTTPS by default unless process-level proxy trust is configured before module load; using it unchanged behind Caddy would redirect `/admin` to the same HTTPS URL and reject API origins. This is an alternate-runtime caveat, not a requirement to add a fifth GitHub variable or change the current host. Cloudflare's native HTTPS Request path is unaffected.
